# Security model

Repo Steward's premise is that an AI teammate is safe to adopt only if its authority is decided outside the model. This document states the boundaries precisely.

## Trust zones

| Zone | Trusted? | Examples |
| --- | --- | --- |
| Committed configuration | Yes (team-reviewed) | `.repo-steward.yml`, presets |
| Deterministic code | Yes | policy engine, executors, schemas, diffing |
| Analyzer output | **No** — schema-checked data | scripted/mock/live proposals |
| Repository content | **No** — data, never instructions | issue/PR bodies, comments, file contents |
| Provider responses | **No** — parsed, validated, retried, else rejected | Anthropic/OpenAI JSON |

## Enforcement is layered

1. **Closed action schema.** Proposals are a discriminated union of 25 action types. Anything else — a novel action name, a malformed payload, an out-of-range confidence — is quarantined at validation with an audit entry (`proposal_rejected_schema`) and never reaches policy.
2. **Deterministic policy.** `evaluateProposal()` reads only the config and the structured proposal fields. Prose cannot change its output. Global safety switches (`safety.*`) precede everything; documentation actions face path allow/deny lists (deny wins) and file/line ceilings computed from real diffs; thresholds gate automatic execution.
3. **Guarded executors.** The simulator executor refuses — unconditionally, under any configuration — source-code modification, pushes to protected branches, and merges; it re-validates docs paths/limits and the close/assign switches at execution time. The real-GitHub executor's entire write surface is issue/PR comments and labels. Tests assert both layers hold at analyzer confidence 1.0 with a deliberately permissive config.
4. **Single execution.** A proposal executes at most once; approving anything not in `awaiting_approval` is a no-op with an explanatory message. Approvals, rejections (with reasons), and failures are appended to the audit log.

## Prompt-injection posture

Live AI mode wraps all repository-derived text in an `<untrusted-repository-data>` fence and instructs the model to treat embedded instructions as data. That instruction is a mitigation, not the boundary: even a fully compromised analyzer can only emit proposals, which still face schema, policy, and executor checks. The worst case of a successful injection is a *bad suggestion* — visible in the Inbox with its evidence and rule — not a bad action. Docs patch bodies are generated by deterministic code in every mode, so injected text cannot become file content via the steward.

## Secrets

- Provider keys live in `.env`, read only by the Express process. `/api/ai/status` returns booleans and model names, never keys. No route echoes environment values; error responses are typed codes + messages without stack traces.
- The CLI/workflows use the ambient `GITHUB_TOKEN`; the code never logs token values.
- The simulator persists only fixture-derived state to `localStorage` — no secrets exist client-side to leak.

## Boundaries by design (not missing features)

- No auto-merge and no steward-initiated merge, simulated or real.
- No source-branch creation and no source-code modification anywhere.
- No real branch/commit/PR creation in the GitHub path in this version — those flows exist only in the simulator, and the docs say so wherever they appear.
- No issue closing or user assignment by default; enabling them requires flipping both the action level and the corresponding `safety.*` switch, and (for real GitHub) they are refused regardless.

## Residual risks worth knowing

- **Comment spam / wrong labels** (real GitHub, writes enabled): bounded by the comments+labels surface and the confidence thresholds; recover by deleting comments and tightening `.repo-steward.yml`.
- **Misleading analysis:** the steward can be wrong. Everything it posts is labeled as steward output with confidence and evidence, and nothing it posts changes what it is allowed to do.
- **Local state tampering:** the simulator trusts its own localStorage (it is a demo of the authority model, not a hardened multi-user product). Executor hard-stops still hold even against hand-edited state/config.
